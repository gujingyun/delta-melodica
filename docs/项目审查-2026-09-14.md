# 项目审查与优化建议（2026-09-14）

审查基线：`e37b9fe`，Windows v0.15、Android v0.6.0。范围包括桌面客户端、Android 客户端、账号服务和官网。本轮只审查、验证和记录，未修改产品代码或线上服务。

**后续修复进度：**第一节列出的五项缺陷已于 2026-09-14 完成修复与回归验证。具体行为、截图和本地修复版见 [README](../README.md) 与 [验证记录](../验证记录.md)。下文保留审查时的基线与原始证据；其余架构、功能扩展和小屏布局建议仍为后续优化计划。

现有项目已经具备较完整的解析、调度、窗口生命周期和账号隔离测试。建议先修复数据保存与导入边界，再拆分桌面控制器、改善曲库操作和小屏适配；现阶段没有证据支持整体重写、替换 Tkinter 或迁移数据库。

## 一、应优先修复的缺陷

### 1. P1：托盘退出绕过编辑器的未保存提示

- 位置：`app.py:1688–1693`；对照 `score_editor.py:470–475`。
- 触发：打开简谱编辑器，修改曲名或谱文，不保存，通过系统托盘“退出”。
- 原因：应用退出直接调用 `score_editor.close(force=True)`，而编辑器的放弃修改确认只在 `force=False` 时执行。
- 本机复现：编辑器快照已改变，确认框调用次数为 **0**，应用与编辑器均关闭，`saved_path` 仍为空。尚未保存的内容被丢弃。
- 建议：正常退出先完成未保存检查，支持保存、放弃、取消；用户取消时不要进入 `closing` 状态。强制关闭仅保留给明确的测试清理等内部路径。无论是否退出，停止演奏和释放按键都应独立执行。
- 验收：编辑器关闭、托盘退出、托盘失效后的退出入口都遵循同一规则；取消退出后仍能继续编辑和保存。

### 2. P2：带 UTF-8 BOM 的曲谱通过导入校验，却无法加载

- 位置：`online_library.py:168`；`app.py:700`、`app.py:725`；`score_editor.py:174`；`account_client.py:248`。
- 触发：将有效的标准曲谱 JSON 保存为带 BOM 的 UTF-8，再通过“导入曲谱 / MIDI”导入。
- 原因：校验使用 `utf-8-sig`，导入随后原样复制；曲库、编辑器与同步读取却使用 `utf-8`。
- 本机复现：校验成功、文件已复制，但载入报 `Unexpected UTF-8 BOM`，没有选中可播放曲目。
- 建议：将曲谱读取集中到一个入口，统一编码兼容、大小限制、格式识别和附注校验；导入与官网下载都复用该入口。
- 验收：同一带 BOM 的 JSON 可以导入、选曲、编辑、重启后读取并参与同步。

### 3. P2：旧版简谱 JSON 能读取，却不能重新导入

- 位置：`app.py:1161–1163`；对照 `app.py:738–740` 与 `account_client.py:248–251`。
- 触发：从旧设备或备份导入 `{"title":"旧格式样例","bpm":100,"score":"1 2 3"}`。
- 原因：导入入口统一交给只接受标准交换曲谱的 `validate_score_file()`；曲库载入和云同步却仍支持旧版 `title/bpm/score` 格式。
- 本机复现：导入报告“不支持的云端曲谱版本”；将同一文件放入隔离曲库后，能正常载入演奏计划。
- 建议：统一识别旧版文本简谱与标准曲谱，校验后迁移或保留可读源文，保证旧曲库的迁移路径。
- 验收：旧版曲库备份可以通过公开界面重新导入，不需要用户手动寻找数据目录。

### 4. P2：游客归属记录损坏会阻止整个客户端启动

- 位置：`account_client.py:30–34`、`account_client.py:91–94`；`app.py:112`。
- 触发：`guest-claims.json` 内容不完整或结构不符合预期。
- 原因：该文件的 JSON 读取异常未转为可恢复状态；`AccountClient` 又在日志和主界面建立前初始化。
- 本机复现：临时数据目录中将记录写成 `{`，构造账号客户端直接抛出 `JSONDecodeError`。应用没有外层恢复分支。
- 建议：保留损坏文件，给出明确恢复提示，暂时禁用归属合并，允许离线查看已有曲谱。不要简单清空归属记录，避免同一批曲目被再次分配给其他账号。
- 验收：记录损坏时仍能进入本地界面和查看诊断；修复记录后能继续原来的继承批次。

### 5. P2：读取失败的曲目无法通过界面删除

- 位置：`app.py:764–766`、`app.py:1251–1256`。
- 触发：选中损坏的曲谱，或上述带 BOM、已经复制进曲库却加载失败的曲谱。
- 原因：读取失败会清空 `current_source`；删除按钮又依赖该字段，而不是列表中选中的文件。
- 本机复现：错误文件仍在列表和磁盘中，`current_source=None`，删除按钮为 `disabled`。
- 建议：将“选中的曲库条目”和“成功加载的乐曲”分开保存。错误条目仍应支持查看错误、定位文件和删除曲库副本，沿用目录边界检查及确认提示。
- 验收：损坏单曲不影响其他曲目，且用户能直接在界面中清理。

| 中 | Windows/Android/网页均实现曲谱校验、同步和游客归属；Android 还明确测试“退出后隐藏已归属游客曲目”，Windows 已改为保留可见 | 增加跨端契约样例及行为对照表。是否保留游客曲目可见属于产品决策，应先明确再统一代码，不能直接将现有 Android 测试判为错误 |

**大曲库测量：**使用 100 个生成的 JSON 文件，每个 30000 个音符、765640 字节，连续调用 `_load_library()` 三次分别耗时 0.905、0.869、0.862 秒，中位数 **0.869 秒**。这段工作在 Tk 主线程发生，期间主窗口不能及时响应。该数据来自合成的较大曲库，不代表普通歌曲的平均体验，也不能直接外推所有设备。建议以真实典型曲库增加计时，再设定加载与交互指标。

## 三、功能改进

1. **先补齐曲库管理。**本地搜索、类型筛选、排序、收藏、最近演奏、完整曲名展示和批量导入进度，优先于继续增加外部搜谱来源。导入失败应逐首报告并允许重试。
2. **补齐云端整理入口。**服务端已有删除 API（`server/accounts.py:403`），并限制每账号 500 首；Windows、Android、网页都缺少对应的云端删除操作。Windows 本地删除后再次同步又可能下载回来，达到配额后普通用户缺少清理途径。应提供“仅移除本地 / 移除云端”的明确操作，并定义本地保留副本是否参与下一次上传，避免删除后又被恢复。
3. **完整备份与还原。**目前云同步有意仅保留标准音符，原谱文字、歌词、局部连奏、每曲设置仍留在本地。增加可导出的完整备份包及恢复预览，明确与云同步的不同；后续若支持跨设备继续编辑，再给编辑附注设计可选版本扩展。
4. **同步显示进度并允许取消。**账号面板处理期间不能关闭，同步逐首串行请求，界面只显示“正在处理”。应展示当前曲目、已完成数量、错误明细，允许取消后重试，并保留已经完成的原子写入。
5. **演奏准备检查与练习模式。**利用现有窗口检测、权限状态、映射和片段功能，清楚显示演奏准备情况；片段上增加循环次数、循环间隔和片段命名。自动停止及焦点检查仍需保留。

## 四、界面优化

视觉检查参考仓库当前版本截图 `website/assets/main-window-v0.15.png`、`android/docs/release-main-v0.6.0.png`，并执行当前代码的桌面冒烟及网页布局测试。下述建议不等同于已完成新界面设计或所有显示器实测。

- **Windows 小屏适配优先。**主窗口最小客户区为 1040×780，初始为 1180×840；780 已高于 1366×768 屏幕的完整高度，尚未扣除标题栏、任务栏。现有布局测试只检查 1180×840 与 1040×780 内部是否越界，没有验证屏幕工作区。建议根据工作区决定初始尺寸，将高级参数折叠或允许内容滚动，固定底部播放/暂停/停止；补测 100%、125%、150% 缩放和多显示器。
- **曲库侧栏提高可读性。**244 像素的固定宽度中，`[类型]` 前缀进一步压缩曲名，现有截图已出现截断。建议可拖动分栏，类型使用短标记，提供完整标题提示和本地搜索。
- **减少首屏说明占用。**保留当前深色与浅绿配色，把目标窗口、权限、热键与校准状态集中呈现；帮助说明放到可展开区域。试听、游戏演奏、暂停和停止继续保持明确区分。
- **Android 按使用阶段组织。**当前长页面先放权限说明，常用曲目、参数和悬浮条操作分散在多个卡片。完成初次授权后可将权限区收成状态行，提高曲库与“显示控制条”的可达性；保留首次引导与失联恢复提示。
- **官网重点维护内容一致性。**本轮 320/390/768/1440 像素检查通过，未发现测试覆盖范围内的横向溢出。优先清理过期文案和维护下载、教程、账号之间的路径。README 顶部已经是 v0.15，但后文仍有“尚未发布”“当前公开版 v0.13”等历史状态，应将其移入按版本归档的记录。
